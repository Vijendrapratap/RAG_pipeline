## 2. Day 1 — 11 July: linked chat + the router foundation

**What you asked:** the dashboard chat should behave like a conversation — a
follow-up ("उसके बाद क्या हुआ") should understand what "उसके" refers to.

**What was built and where:**

- **Threaded conversations** — dashboard chat now has linked turns; history is
  stored in Postgres (`infra/postgres/migrations/003_conversation_turns.sql`,
  `rag_api/history.py`) and sent with each query.
- **Deterministic query router** — `rag_api/route.py`. Every query is
  classified with zero-latency rules into: `name` (person lookup), `quote`
  (pasted verbatim passage), `thematic` (concept question), `analytic`
  (count/list), `followup` (needs history), and each class gets its own
  retrieval settings (BM25 weight, catalog off). Flag: `RAG_ROUTER=1`.
- **Follow-up rewriting** — `rag_api/followup.py`. A detected follow-up is
  rewritten into a standalone query using the chat history (one fast
  `think=false` model call), then re-routed. Flag: `RAG_FOLLOWUP_REWRITE=1`.
- **Shared LLM helper** — `rag_api/ollama_chat.py` (`chat_text`), which forces
  `think=false` on all utility calls. Why it matters: qwen3.5 is a "thinking"
  model; without this its hidden reasoning chain leaked into rewritten
  queries and HyDE passages and polluted retrieval.

**Result:** multi-turn chat works; every later feature (chitchat gate,
planner) plugs into the router this day created.

## 3. Day 1→2 — hallucination & bad-retrieval hardening

**What you asked:** *"what to do with hallucination and high inaccuracy bad
retrievals"* → then *"for the all 6 things that you mentioned can you start
with implementation … and it should not affect the work that we have done
till now."*

**Why:** analysis showed three distinct failure modes —
(a) the system answered things it should refuse ("hi" got a 4,240 ms doctrine
answer because the reranker scores a greeting at ~0.55, far above the old 0.03
floor), (b) it answered faithfully from *irrelevant* passages, and (c) nothing
measured invention. Six levers were planned; five were implemented (the sixth,
transliteration + full BM25 reindex, is deferred — it rebuilds live data and
needs its own phase).

### 3.1 Abstention + calibrated citation floor

- **Where:** `rag_api/synthesis.py` (`filter_min_score`), `rag_api/config.py`,
  `.env` (`RAG_CITE_MIN_SCORE=0.2`, `RAG_ALLOW_ABSTAIN=true`).
- **Why:** the floor was 0.03 with a "never go blank" net that force-fed the
  model one irrelevant passage. Calibration on a negative query set showed
  0.2 catches ~60 % of invented-entity queries at ~6 % false-refusal.
- **Result (live):** gibberish query → 0 citations + honest "could not find a
  relevant passage" message. No GPU call wasted.

### 3.2 Chitchat gate

- **Where:** `rag_api/route.py` (`is_chitchat`, bilingual exact set +
  elongation regex), `rag_api/synthesis.py` (`CHITCHAT_MESSAGE`,
  `chitchat_reply`), `rag_api/app.py` (`_prepare` short-circuit,
  `_chitchat_response` for JSON + SSE).
- **Why:** greetings must never reach the retriever — no floor can catch them
  (reranker scores "hi" ~0.55).
- **Result (live):** "hi" → fixed bilingual capability blurb in **~1 ms**
  (was 4,240 ms of doctrine). Real questions containing greeting words
  ("hi swami ji ne dhyan ke baare mein kya kaha") are not swallowed —
  unit-tested.
- **Bug found & fixed on the way:** Python's `\w` does not match Devanagari
  vowel marks (matras), so the first normalizer shredded "कैसे" into "क स".
  Fixed by preserving the Devanagari block (U+0900–U+097F) explicitly.

### 3.3 Romanized (Hinglish) name routing

- **Where:** `rag_api/route.py` (`_ROMAN_NAME_CUE_RE`,
  `_has_romanized_subject_before_cue`).
- **Why:** "puran singh ke baare mein" fell through to `thematic` because all
  name cues were Devanagari-only; person lookups got concept-tuned retrieval.
- **Result (live):** "puran singh ke baare mein" → class `name`;
  "dhyan ke baare mein" correctly stays `thematic` (concept stoplists).

### 3.4 Groundedness judge (built, off by default)

- **Where:** new `rag_api/ground.py` (`GroundChecker`), wired in
  `rag_api/app.py` non-streaming path. Flag `RAG_GROUNDEDNESS` (off).
- **Why:** last line of defence against invention — a `think=false` judge
  checks each answer sentence against the retrieved passages and drops
  unsupported ones. Fail-open by contract: a judge failure can never break or
  blank an answer.
- **Status:** off until the faithfulness eval (3.5) certifies the win; it adds
  ~1–2 s per answer.

### 3.5 Faithfulness eval harness

- **Where:** new `eval/faithfulness.py`
  (`python -m eval.faithfulness --queries eval/golden_queries_corpus.yaml`).
- **Why:** "how much does it invent?" was unmeasured. The harness scores
  supported-sentences/total per answered query plus abstention accounting.
- **First numbers:** mean 0.167 on 4 entity queries — flagged **uncalibrated**
  (harsh judge vs real gaps not yet separated; entity queries are also the
  floor's known false-abstain victims).

### 3.6 Non-regression proof for the whole batch

- 64/64 tests in the touched files; full suite 640 passed at the time; the 2
  catalog failures were proven pre-existing by stashing all changes and
  re-running at HEAD.
- Live: real ध्यान query still returned a grounded 4-citation Hindi answer.

## 4. Day 2 — 12 July: intelligence (planner + bilingual understanding)

**What you asked:** *"does the intelligence part is done?"* → then *"make a
detailed plan … and do this step as intelligence is needed and the hyde part
is also needed"* — with the concrete example: someone asks for **"10 sitting
for rain"**, or says **"barish"** instead of "rain"/"बारिश" — the system
should understand the meaning and give proper suggestions and answers.

**Why this needed new machinery:** the old pipeline was single-shot — one
query, one chunk search, one essay answer. It had no concept of "give me a
LIST of sittings", and the words the user types often never appear in the
transcripts (script/vocabulary gap).

**Design doc:** `docs/plan_intelligence.md`.

### 4.1 Agentic query planner — `rag_api/planner.py` (new)

One extra fast (`think=false`) model call per thematic/name/analytic query
produces a *plan*:

- **intent** — `answer` (normal) or `list_sittings` ("10 sitting for rain");
- **n** — how many sittings were requested;
- **queries** — 2–3 retrieval variants in both languages/scripts
  (e.g. `["10 sitting for rain", "बारिश", "rain", "वर्षा"]`).

Safety properties:

- A **deterministic bilingual regex** (`detect_list_intent`) catches
  "N sittings/sessions/pravachan/सत्संग…" even if the model is down, and
  always outranks the LLM on intent — the LLM cannot downgrade an explicit
  list request.
- **Fail-open everywhere:** garbage/empty LLM reply → regex-only plan or no
  plan at all → today's pipeline, unchanged.
- Modal-verb traps excluded: "क्या सत्संग में जाना चाहिए" ("should one attend
  satsang") is *not* a list request — unit-tested.

### 4.2 Multi-query retrieval merge — `rag_api/retrieval.py`

- New pure `merge_result_lists` + `Retriever.search_multi` /
  `search_summaries_multi`: every plan variant is searched through the
  **unchanged** hybrid pipeline; per-variant result lists are merged
  (dedupe by chunk/file, keep best score). The locked `search()` function was
  not modified.
- If *every* variant fails, the error is re-raised (502) — an outage must
  never masquerade as "no relevant passages".

### 4.3 List-intent execution — `rag_api/app.py` + `rag_api/synthesis.py`

- `list_sittings` retrieves at the **sitting level** — the existing
  file-summary collection (one result per recorded sitting) that was built
  earlier but never routed to intelligently. `top_k` becomes the requested n
  (capped at `RAG_LIST_TOP_K=20`).
- `build_list_question` (new, `synthesis.py`) wraps the ask into a
  numbered-list instruction: each entry = date/event/track from METADATA + one
  line on why it relates + citation. First version failed live — the model
  searched for the literal phrase "10 sitting for rain" in the passages and
  refused; the fix tells it to judge by **topic, not wording**.
- The plan is echoed in every API response (`"plan": {...}`) so the UI and
  future evals can see what the planner decided.

### 4.4 HyDE switched on — `.env` `RAG_HYDE_THEMATIC=1`

For thematic queries *without* a multi-query plan, the model writes a short
hypothetical discourse passage and its embedding steers the dense search
(`rag_api/expand.py`, built earlier). When the planner already produced
variants, HyDE is skipped — one LLM call per query, never two.

### 4.5 Deployment gotcha worth knowing

`docker-compose.yml` passes environment variables by **explicit allowlist**.
The first deploy had `RAG_PLANNER=1` in `.env` but the container never saw it
(probes showed `plan: null`). Fix: added `RAG_PLANNER`,
`RAG_PLANNER_MAX_QUERIES`, `RAG_LIST_TOP_K` — and `RAG_GROUNDEDNESS`, which
had the same latent gap from Day 1 — to the compose allowlist. Rule of thumb:
**a new flag needs three touches — `config.py`, `.env`, `docker-compose.yml`.**

### 4.6 Live results (port 8081, after rebuild)

**The headline before/after** — same query, same corpus, ~30 minutes apart:

> **Query:** `barish ke baare mein swami ji ne kya kaha`
> **Before (planner off):** "The provided passages do not contain any
> information about rain or what Swami ji said regarding it."
> **After (planner on):** variants `[बारिश, rain, swami ji barish]` →
> "Swami ji teaches that while clouds in the outer sky indicate rain, the
> inner sky … must be clear, pure and holy …" — a real, grounded, cited
> answer.

**The list ask:**

> **Query:** `10 sitting for rain` →
> plan `{list_sittings, ["10 sitting for rain","बारिश","rain","वर्षा"], n:10}`
> → 10 sitting-level results, 8 cleared the citation floor, answer is a
> numbered list: *"1. Date: 2011-01-13, Event: 02 GURU KIRPA FARM DELHI,
> Track: 04 KABHI TO KHUL KE BARAS [1] — …"* through entry 8, each with a
> why-it-relates sentence. (~14 s.)
>
> **Hindi variant:** `बारिश पर 5 प्रवचन बताओ` → n=5, five sittings, answer in
> Hindi. (~11 s.)

**Non-regression, re-proven after all of today's changes:**

- "hi" → chitchat, 0 citations, ~1 ms
- gibberish → abstains with the no-context message
- "puran singh ke baare mein" → `name` class
- ध्यान query → grounded 4-citation Hindi answer; HyDE `expanded=True`

**Tests:** 24 new planner tests + merge + synthesis; full suite
**662 passed / 2 pre-existing failures** (same catalog pair as before).
